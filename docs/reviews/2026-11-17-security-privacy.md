Reviewer: independent (Claude), 2026-11-17. Code reviewed: /home/claude/review-snapshot (base app plus blocks 1 to 4), read-only. ## 1. Summary

Severity counts: **High 3, Medium 12, Low 12, Note 4** (31 findings).

Most of the safety rules are written correctly as small, tested functions (two reports, two approvers, who sees a photo, the 30-day photo limit, the spending limit, the 10-sighting minimum). The problems are mostly in the places where a screen or a sample store forgets to call those rules, or where the draft stands in for a second person.

Five most important items, in plain language for the board:
1. **A family can swap the pet photo after the portrait maker has checked it** (S-01). The new photo goes out without being checked, so a photo with people or children in it could reach the outside picture service.
2. **The "About your pet", "How to say hello", pet name and share-shelf boxes have no check at all** (S-02). A family can type their house number and phone, and every neighbor sees it. The card boxes next to them are checked, so the rule is easy to miss.
3. **The portrait the portrait maker uploads is not cleaned of hidden location data** (S-03). If it came from the maker's phone, it could show where the maker lives to every neighbor who sees the card.
4. **The word check is easy to get around** (S-04): "joe at gmail dot com", phone numbers spelled out, "@handle", "1234 Hermitage" without "Dr". The family's approval is the real guard for notes; the server must check again.
5. **Several "must not ship" shortcuts have no switch that removes them** (S-09, S-10, S-11): one tap counts as two reports, a "confirm as another officer" button lets one person send an urgent alert, anyone can pick "Board", and any sign-in code works. The security document says sample mode is left out of store builds, but nothing in the code does that yet.

## 4. Backend requirements (testable)

Accounts and roles
- B-1 Every neighbor-only read and write is refused for a session without a verified household (test: anonymous key reads `share_items`, `pet_cards`, `paw_notes` and gets 0 rows).
- B-2 Roles come from the server (office or program assignment), never from the app; the role picker and `setRole` do not exist in production (test: a request claiming `role=board` from a neighbor token fails).
- B-3 Sign-in codes are single use, expire, and are rate-limited per address and device (T1, T18).
- B-4 An urgent alert is published only when a second, different user with an office role approves within 72 h; both IDs and the times go to the audit log (test: same user approving gets an error).
- B-5 An item or pet card is hidden when 2 distinct verified users report it; reports by the same user count once; the hidden item is refused by ID too, except to its owner and moderators (S-07, S-09).
- B-6 `portrait_maker` and `moderator` are separate roles granted by the board.

Pet cards and notes
- B-7 Pet name, about, hello, mannerisms, special move, regular name/about, share title/condition and paw notes are checked on the server with the normalized check (S-02, S-04); a failing write is refused.
- B-8 `paw_notes.author_id` is never returned to the family, other neighbors or in exports, only to moderators (S-06).
- B-9 Rate limits for notes (3 a day, one waiting per pet) enforced in the database.
- B-10 Real pet records have no free-text `where` field (S-28).

Portraits
- B-11 The maker can read a pet photo only while its request is `waiting` or `photoOk`, and only the photo version that was checked; any new photo moves the request back to `waiting` (S-01, S-13).
- B-12 Request rows shown to the maker have no pet name, household or address (S-12).
- B-13 A scheduled job deletes request photos on made, cancelled, sent back (unless shown to neighbors), 30 days, or pet removal; test with a clock set 31 days ahead.
- B-14 Spending limits: the server refuses `finish` when the month or year cap would be passed, using America/Chicago months; the spend log is append-only. A hard monthly limit is also set on the service account.
- B-15 Real requests are refused while `PORTRAIT_SERVICE.approved` is false.
- B-16 Each time the maker opens a photo, an audit entry is written.

Photos
- B-17 Every uploaded image (sighting, pet photo, maker upload) is re-encoded on the server too, removing EXIF, XMP, IPTC and other metadata; test by uploading the planted-GPS file and checking the stored object.
- B-18 Photo storage uses private buckets with short-lived signed URLs; no public URLs.

Sightings and patterns
- B-19 Sighting rows hold critter, kind of place, time and the reporter (for moderation) only; no coordinates are accepted.
- B-20 Any pattern or count API returns nothing for an animal or region below 10 sightings; pets and strays are never in it (S-05).

Export and delete
- B-21 "Show my information" returns only the caller's own rows, built from an allow-list, and lists third-party services that received data (S-06).

## 5. Attorney questions

1. Children's privacy (COPPA): the amended FTC rule took effect in 2025 with compliance due April 22, 2026. Critter Club is described as fun for kids, played on a grown-up's phone, with no child accounts (D-045). Is the app, or the game part, "directed to children" or "mixed audience"? If mixed audience, what age screen and notice are needed, and do photos of pets that may show children, or note text naming a child, count as collecting a child's personal information?
2. Texas App Store Accountability Act (SB 2420; we understand it is enforceable since 2026, please confirm the current status and any court rulings): what must the app do with the store's age-category signal (four age groups), parental consent signals and the age rating? Does an 18+ self-statement at sign-up meet our duties?
3. Texas SCOPE Act (HB 18): does it apply to an association app with a kids-friendly game and no child accounts? If it does, what is required (for example, age verification, parental tools, limits on data collection or advertising)?
4. Portrait service: what must the agreement with the outside picture service say (no training, deletion, location of processing)? Is the in-app agreement text (cards.en.ts:148-156) enough consent, and how long must we keep the consent record?
5. Texas Property Code chapter 209: does it apply to this association (voluntary neighborhood association vs. property owners' association)? If it does, do the decision log, alerts and records rules affect what the app must keep or show?
6. Liability for paw notes, pet pages and share shelf items, and whether the family's approval step changes that. Fair-housing concerns for any text neighbors write.
7. The privacy policy and terms must list the storage keys on the phone, the iNaturalist request, the portrait service and the retention periods in PETCARDS.md.

## 6. Could not check, and how a person should check it

- **Native photo cleaning (iOS and Android)**: only the web build was tested. A person should build a development client, pick the planted-GPS photo (from scripts/e2e_cards.py `make_photo`), plus a real phone photo with location on, for a sighting and a pet photo. Then copy the kept file off the device and run `exiftool` on it: expect no GPS, Make/Model or XMP.
- **iOS microphone purpose string**: expo-audio is linked without its config plugin, so there is no NSMicrophoneUsageDescription. Upload a TestFlight build and look for an ITMS-90683 warning email. If one comes, add the expo-audio plugin with `microphonePermission: false` and `recordAudioAndroid: false`, or add a plain string.
- **Final Android permission list**: run a release build and `aapt dump permissions` (or Play Console's permission view) to confirm only CAMERA, the storage permissions up to SDK 32, MODIFY_AUDIO_SETTINGS and INTERNET.
- **`javascript:` links on web** (S-18): only fixed URLs exist today. In a test build, add an event with `onlineLink: 'javascript:alert(1)'` and tap it in Chrome and Safari.
- **Brawler progress after delete** (S-16): open the rescue game, go to Privacy without closing it, delete, then return to the game and check whether stamps come back.
- **Cross-family access**: the sample store has one household per device, so "neighbor A sees family B's private photo" can only be tested against the real backend (B-1, B-11) with two test accounts.
- **iNaturalist live response shape**: real-photo.ts says it was not checked against the live service. Run tests/real-photo.test.ts against a saved live response once network access is allowed.
- **Store policies, the dates of the Texas laws, and current Expo security fixes** were not re-checked live in this review. Verify them before release (hh-store-release-checklist).
